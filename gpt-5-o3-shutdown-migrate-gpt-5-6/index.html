gpt-5 和 o3 下线前，迁移到 gpt-5.6 要改哪些地方

OpenAI 在 2026-06-11 通知使用旧版 GPT-5 和 o3 快照的开发者：这些模型将于 2026-12-11 从 API 移除。官方给出的替代是 GPT-5.6 家族：gpt-5 和 o3 换 gpt-5.6-sol，gpt-5-mini 换 gpt-5.6-terra，gpt-5-nano 换 gpt-5.6-luna，gpt-5-pro 和 o3-pro 换 gpt-5.6-sol 加 reasoning.mode: pro。官方升级指南明确提醒不要只做模型名替换：推理强度默认值、Chat Completions 里的函数调用、Pro 模式写法都可能让迁移后的请求变慢、变贵或出现不兼容。本页按官方文档逐项说明。

哪些模型会下线，分别换成什么？

官方下线公告（https://developers.openai.com/api/docs/deprecations ，条目「2026-06-11: GPT-5 and o3」）列出的模型，下线日期都是 2026-12-11：gpt-5（gpt-5-2025-08-07）换 gpt-5.6-sol；gpt-5-mini（gpt-5-mini-2025-08-07）换 gpt-5.6-terra；gpt-5-nano（gpt-5-nano-2025-08-07）换 gpt-5.6-luna；gpt-5-pro（gpt-5-pro-2025-10-06）换 gpt-5.6-sol 并设 reasoning.mode: pro；o3（o3-2025-04-16）换 gpt-5.6-sol；o3-pro（o3-pro-2025-06-10）换 gpt-5.6-sol 并设 reasoning.mode: pro。

按官方政策，宣布弃用后模型立即进入弃用状态，到下线日期后该模型在 API 中不再可用；部分开发者可以联系销售通过专用容量继续使用。官方文档没有写明下线后请求会返回哪种错误码，所以不要等到报错再处理，应在 12 月 11 日之前完成切换和验证。

要用程序检查自己用到的模型有没有下线日期，可以调用 List models（GET /v1/models）或 Retrieve a model，看每个模型的 shutdown_date 字段：有值时是 YYYY-MM-DD 格式的日期，没有公布下线日期时为 null。

sol、terra、luna 怎么选？gpt-5.6 这个名字指向谁？

官方升级指南（https://developers.openai.com/api/docs/guides/upgrading-to-gpt-5p6-sol）把 GPT-5.6 当作一个家族，按原来的角色对应：原来用不带后缀的 GPT-5 旗舰、GPT-5.5 或 GPT-5.4 旗舰的，起步换 gpt-5.6-sol；原来用 mini、追求均衡成本的，换 gpt-5.6-terra；原来用 nano，做分类、抽取、路由、高并发或对延迟要求严格的，换 gpt-5.6-luna。指南特别提醒，不要把所有旧模型都换成 Sol，否则原本刻意选低成本、低延迟模型的流程会变慢、变贵。

gpt-5.6 是别名，按 Sol 的模型页（https://developers.openai.com/api/docs/models/gpt-5.6-sol）说明，它会路由到 gpt-5.6-sol。官方建议默认写明确的 gpt-5.6-sol；如果用别名，验证时记录返回的 response.model，不要假设别名和明确型号在用量面板、限流配置、统计和账单里显示一致。

上下文方面，Sol 和 Terra 的模型页写的是 1,050,000 上下文、最多 128,000 输出 token；Sol 和 Terra 输入超过 272K token 时整次请求的计价方式会变化，具体以官网价格页为准。升级指南还提醒要对照模型页核对 Luna 的上下文上限，原来跑长上下文的任务换 Luna 前要用最长的真实输入测一次。

推理强度：不写 effort 时默认值会变成 medium

GPT-5.6 三个模型页写的 reasoning.effort 取值都是 none、low、medium（默认）、high、xhigh、max。推理指南（https://developers.openai.com/api/docs/guides/reasoning）也说明，不写 effort 时 GPT-5.6 默认 medium。升级指南把这一点列为主要风险：原来实际推理强度是 none 的调用，换模型后如果还不写，会变成 medium，结果是更慢、更贵，而且会和 Chat Completions 的函数调用冲突（见下一节）。

官方建议的做法是：原来写明了 effort 的，第一轮迁移保持同样的值（前提是新模型支持）；原来没写、但清楚旧模型实际默认值的，只有在 GPT-5.6 的默认值会改变行为时才显式写上；不清楚旧值的不要猜，标出来，用旧模型和新模型在可能的基准值上对比。基准跑通后，再试同一档和低一档。xhigh、max 只用在评测证明有明显收益的高难任务上。

如果旧代码里用了 minimal，要注意 GPT-5.6 模型页列出的取值里没有 minimal，需要换成列表里的某一档，并用代表性任务对比效果和耗时。

两种接口的写法不同：Responses API 写成 "reasoning": {"effort": "none"}，Chat Completions 写成 "reasoning_effort": "none"。

Chat Completions 里用函数调用的，迁移后最容易出问题

升级指南把这一条称为最重要的接口检查：对 GPT-5.6，Chat Completions 里的函数工具只在实际推理强度为 none 时兼容；需要推理又需要工具的，应使用 Responses API。

因为 GPT-5.6 默认是 medium，所以一个只把 model 改成 gpt-5.6-luna、带着 tools、却没写 reasoning_effort 的 Chat Completions 请求，正是指南列出的不安全写法。要继续用 Chat Completions 和函数工具的低延迟流程，应显式写 "reasoning_effort": "none"。

如果这个流程既需要推理又需要工具：能改代码就迁到 Responses API；暂时改不了就把它记为兼容性阻塞项。指南明确反对用删掉工具、去掉必要的推理来让请求跑通。如果 none 的写法被线上接口拒绝，按指南要求记录完整请求和报错，不要自己编绕过办法。

gpt-5-pro、o3-pro 要改成 reasoning.mode: pro

GPT-5.6 没有单独的 Pro 型号。升级指南说明，GPT-5.6 Pro 是基础模型加推理模式，不要去找或编造 gpt-5.6-pro 这样的模型名。写法是在 Responses API 请求里使用 model: gpt-5.6-sol，并在 reasoning 里同时写 "mode": "pro" 和 "effort": "medium"。

规则有三条：只能用 Responses API，不能用 Chat Completions；Pro 模式支持的推理强度从 medium 起；mode 和 effort 是两个独立的设置。推理指南补充：不写 effort 时，两种模式下 GPT-5.6 都默认 medium；Pro 模式会做更多模型计算，token 用量和费用都会增加，这些 token 按所选模型的标准单价计费，单价以官网价格页为准。

原来不是 Pro 的调用，迁移时不要顺手开 Pro。指南建议把 Pro 当作单独的一步，和普通 Sol 迁移分开评估质量、总耗时和实际计费 token。

还有哪些行为会悄悄变化？

提示缓存：升级指南说明 GPT-5.6 的隐式缓存把断点放在最新的用户或工具消息附近，不再按 128 token 取整。如果提示词是大段固定前缀后面接一段会变的内容，即使前缀没变也可能命中不了。迁移后要对比 cached_tokens、cache_write_tokens、耗时和费用；新旧模型共用一套请求构造代码时，不要把 GPT-5.6 才有的缓存字段发给旧模型。

多轮推理上下文：推理指南说明 GPT-5.6 家族默认 reasoning.context 为 all_turns，会把前几轮可用的推理带入下一轮；更早的模型默认 current_turn。升级指南要求：手动回放对话时，条目类型、ID、call_id 等要原样保留，回放不完整可能在没有报错的情况下降低质量或中断工具调用；如果启用持久推理并手动回放，要保留之前每一轮的用户输入和相关输出项，不能只保留助手文字；在 store: false 或零数据保留的情况下，要回传推理项及其 encrypted_content。

图片和 PDF：图片的 detail 不写或设为 auto 时可能保留原始尺寸；Responses 里的 PDF/文件输入不写 detail 或设为 auto 时可能使用高精度页面图像。对成本和耗时敏感的流程，迁移前后要量一下输入 token，并把 detail 写明确。

迁移步骤和验证清单

第一步，盘点：不只搜模型名，还要查环境变量、命令行参数、配置默认值、模型白名单、正则和枚举、价格元数据、前端模型选择列表、测试和评测基线。升级指南把「只改了模型名，漏改白名单、价格元数据、测试和模型选择界面」列为迁移风险之一。

第二步，按角色选 Sol、Terra 或 Luna，并把原来的实际推理强度显式写进新请求；用 Chat Completions 加函数工具的，确认写了 reasoning_effort: none，或者迁到 Responses。

第三步，按官方的对比矩阵做测试：旧模型加旧提示词；新模型加同样提示词和保留的推理强度；新模型降一档推理强度；需要时再加最小的提示词或接口修改；Pro 等可选功能单独测。

成功标准：代码里已没有调用这六个将下线模型的地方；新请求返回的 response.model 是预期的 gpt-5.6 型号；结构化输出能正常解析，工具调用和完成率不下降；耗时、输入/输出/推理/缓存 token 和每次成功任务的成本都在可接受范围内。全部在 2026-12-11 之前完成。

如果通过中转服务调用，先在它的模型列表里确认 gpt-5.6-sol、gpt-5.6-terra、gpt-5.6-luna 是否可用，再用一条带 reasoning 参数的请求确认参数能原样传到上游；价格以官网价格页为准。
